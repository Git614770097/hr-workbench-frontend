# 功能取舍建议：优化 / 新增 / 删除

- **日期**：2026-10-20
- **依据**：全仓代码通读 + `docs/ai-endpoint-audit-2026-10-14.md` 线上使用数据 + git 历史
- **前置判断**：见第 0 节，它决定后面所有取舍

---

## 0. 先解决一个矛盾：产品边界正在漂移

`src/pages/Help.tsx:54` 对用户的官方说明是：

> 「一套面向招聘业务的人才管理系统，覆盖『人才从入库到入职』的全过程……**不含员工花名册、薪资绩效等入职之后的模块**。」

但代码里已经有：

| 已有能力 | 所在位置 | 属于哪个阶段 |
|---|---|---|
| 合同到期 / 续签提醒 | `talents.contract_end` + `reminders` | 入职后 |
| 试用期转正提醒 | `talents.probation_end` | 入职后 |
| 社保参保台账 / 增减员待办 | `talent_social` + `socialTaskStmts` | 入职后 |
| 离职倒计时 | `talents.resignation_date` | 离职 |

**这不是 bug，是战略选择没做完。** 现在的状态是「嘴上说只做招聘，手上已经在做在职管理，但只做了最麻烦的三块（合同/社保/离职），没做最基础的一块（组织架构/花名册）」。

后果很具体：
- 用户心智混乱——「这系统到底管不管我入职后的人？」
- 合同和社保功能**缺少组织维度**（没有部门树、没有汇报线），只能按人一条条看，做不了「某部门今年合同到期人数」
- 销售话术与产品能力脱节——`Landing.tsx:142` 宣传「与企业微信打通」，但代码里 **`feishu_open_id` / `wecom_userid` / `notify_channel` 三个字段只有 schema、零实现**（`grep feishu\|wecom` 在 `src/worker` 下无任何命中）

### 两条路，选一条

**路线 A：守住「招聘」边界（推荐给当前阶段）**
- 砍掉合同/社保/离职三个模块，或降级为「入职交接清单」的一部分
- 把省下的精力投到招聘链路的深度：渠道 ROI、面试官协同、候选人体验
- 优点：与 Help 文案、与「人才库」的定位一致，功能聚焦，销售好讲
- 代价：已有付费用户如果正在用社保台账，会反弹（需要先确认使用情况）

**路线 B：承认做「招聘 + 在职」（推荐如果有 >3 个客户在用合同/社保）**
- 补齐组织架构（部门树 + 汇报线 + 编制）
- 补离职闭环（交接清单、离职面谈、权限回收）
- Help 文案改写，Landing 同步
- 优点：客单价能上去，留存更好（入职后不迁走）
- 代价：正面撞北森、Moka、i人事，功能深度拼不过

**怎么判断走哪条？** 查一下 `talent_social` 有多少条非空记录、`contract_files` 有多少文件、`contract_end` 有多少人填了。如果这三个数加起来不到 10，路线 A；超过 50，路线 B。

> ⚠️ 在做出这个决定之前，**不要新增任何「入职后」的功能**。否则两条路都走不顺。

## 1. 需要优化的功能

按「用户痛感 × 修复成本」排序。

### O1【P0】移动端缺「面试」——最高频场景没入口

`src/mobile/tabs.tsx` 只有 4 个 Tab：待办、看板、人才库、概览。

HR 在手机上最高频的三个动作是：**看今天有几场面试、看候选人简历、处理待办**。现在「面试」完全没有移动端页面，用户只能打开桌面版。

- 建议：新增 `/m/interviews`（只读列表 + 一键拨号 + 快速记评价），放在「待办」旁边
- 同时**删掉 `/m/funnel`**——漏斗概览在手机上没人看，占了一个宝贵的 Tab 位
- 成本：1 个页面，复用 `MTasks` 的卡片模式，约 300 行

### O2【P0】人才检索是 `LIKE '%关键词%'`，全表扫

`talents.ts:244-263` 的 7 个字段全部 `LIKE '%x%'`。SQLite 对前置通配符**无法使用索引**，等于每次搜索全表扫描 + 7 次字符串匹配。

当前数据量无感，但这是「找人」的核心路径，也是最容易随数据增长崩掉的地方。

- 短期：加 `name` 前缀索引不解决（前置 % 用不上），改为**拼音首字母 + 全拼字段**（`name_pinyin`、`name_initials`），搜索时先精确匹配拼音
- 中期：上 D1 的 FTS5 虚拟表，把 name/company/title/skills/notes 建全文索引
- 成本：FTS5 约 1 天（含数据回填 + 触发器同步）

### O3【P1】通知渠道只有一个，schema 里三个是死的

`users` 表有 `notify_channel`（pushplus/feishu/wecom）、`feishu_open_id`、`wecom_userid`，但：

- `src/worker` 下 **零处** 引用 feishu/wecom
- 前端 **零处** 渠道选择 UI
- 唯一实现的是 PushPlus（`reminders.ts:60`），依赖用户自己去第三方注册拿 token

这意味着：**企业客户基本用不了到期提醒**——让 HR 去注册一个个人微信推送服务，在企业环境里是过不去的。

- 建议（按性价比）：① 邮件（SMTP/Resend，最通用）→ ② 企业微信群机器人 webhook（一行 URL 即可，最轻）→ ③ 飞书
- 同时删掉 `notify_channel`/`feishu_open_id`/`wecom_userid` 三列，或补齐实现——**不要留着不用**
- 成本：企业微信 webhook 半天；邮件 1 天

### O4【P1】批量操作缺「批量加入岗位」

现有：`batch/tags`、`batch/delete`、`batch/stage`。

缺：批量把 N 个候选人加入某个岗位的流程（`talent_jobs`）。这正是「一次收到 20 份简历，筛出 8 个推给用人部门」的真实场景，现在只能一个个点。

- 成本：半天，复用 `AddToPipelineModal`

### O5【P1】漏斗只统计「量」，不回答「为什么慢」

`pages/Funnel.tsx`（1115 行）展示了各阶段人数和转化，但缺三个 HR 最想看的数：

| 缺失指标 | 为什么重要 |
|---|---|
| **平均阶段停留时长** | 「卡在复试」到底是面试官排不开，还是候选人犹豫？ |
| **各阶段流失率趋势** | 本月比上月恶化了吗 |
| **渠道转化对比** | 猎聘来的人 offer 接受率比内推低多少 |

数据都在（`job_stage_logs` 有完整流转时间戳），**只是没算**。

- 成本：后端 2 个聚合查询 + 前端 1 个图，约 1 天

### O6【P1】面试官协同缺失——面试官根本不是系统用户

现在面试官是 `interviews.interviewer` 一个**自由文本字段**（多人用顿号分隔）。后果：

- 面试官收不到任何提醒（提醒只推给 HR）
- 面试官无法填评价，只能 HR 转述，`dept_result`/`dept_score` 靠 HR 代填——**用人部门意见失真**
- 这正是 `interview-questions`、`candidate-summary` 线上 0 使用的深层原因：**面试评价本身就是空的**（审计文档也指出「需先有面试评价才可用」）

- 建议：给面试官发**带 token 的一次性评价链接**（免登录），填完回写 `interviews`。不需要给面试官开账号，成本可控
- 成本：2 天（含链接签名与过期）

### O7【P1】没有字段级权限——薪资和手机号对所有 HR 可见

13 个菜单 key 是**页面级**权限。但同一个「人才库」页面里：

- 猎头/初级 HR 该看到候选人手机号吗？
- 用人部门该看到 `expected_salary` 吗？

现在只要有 `talents` 权限，全字段可见。这在多人协作、尤其是有外部猎头账号的场景下是硬伤。

- 建议：在 `roles` 上加 `field_masks`（JSON 数组，如 `["phone","expected_salary"]`），返回前统一脱敏
- 成本：后端 1 处中间件 + 前端展示兼容，约 1 天

### O8【P2】手动新增人才无查重

导入时有查重（`talents.ts:1138`：phone 精确 + name+city 组合），但 `POST /api/talents` 手动新增**没有**。同一个候选人被两个 HR 各录一次，是很常见的。

- 成本：2 小时，复用导入的查重逻辑，返回「疑似重复」让用户确认

### O9【P2】5 个零使用 AI 端点的入口曝光

按审计文档：`interview-questions`、`candidate-summary`、`approval-summary`、`next-step`、`resume-optimize` 线上从未成功生成过。

- 其中 `next-step`（看板卡片按钮）最可惜——它是唯一「在决策现场给建议」的 AI，位置不显眼导致没人点
- 建议：看板卡片上把 `next-step` 从图标按钮改成卡片底部的文字链接（「下一步怎么办？」），预期使用率能起来
- 其余 4 个：先修 O6（面试官评价），`interview-questions` 和 `candidate-summary` 的输入自然就有了

## 2. 需要新增的功能

### N1【P0】操作审计日志——当前最大的合规缺口

全仓 `grep audit` **零命中**。也就是说：

- 谁在什么时候看了谁的简历——无记录
- 谁导出了 200 条人才数据——无记录
- 谁改了某人的期望薪资——无记录
- 谁删了一个人才档案——无记录

一个存着几十万条手机号、简历、背调结论的系统，**没有任何访问审计**。这在《个人信息保护法》下是实质风险：一旦发生数据泄露，无法证明「我们尽到了管理义务」；一旦员工离职带走数据，无法追溯。

已有基础很好：`job_stage_logs` 已经证明了「流转留痕」这个模式是对的，照搬到全局即可。

- 表：`audit_logs(id, ts, user_id, user_name, action, target_type, target_id, detail, ip, ua)`
- 埋点位置：所有 `DELETE`、批量操作、导出、简历/合同/背调报告**查看**、权限变更
- 查询页：admin 专属，按人/按对象/按时间筛
- 成本：3 天（中间件 + 埋点 + 查询页）

> 这一项建议**优先于所有新功能**。它不是「nice to have」，是能不能卖给正规企业的门槛。

### N2【P1】招聘渠道 ROI——HR 最想给老板看的数

`talents.source` 已有（boss/liepin/51job/内推/校招），但没有**成本**字段，所以算不出「每个渠道花多少钱招到一个人」。

- 加 `jobs` 或全局的渠道费用录入（按月/按岗位/按成功付费三种模式）
- 出「渠道成本 × 入职人数 = 单人招聘成本」对比
- 成本：2 天
- 价值：这是 HR 向老板证明自己价值的唯一硬指标，也是这个产品最容易做出差异化的地方

### N3【P1】核心人效指标看板

漏斗有阶段数据，但缺招聘行业的标准北极星指标：

| 指标 | 数据是否已有 |
|---|---|
| Time to Hire（岗位开启→入职天数） | ✅ `jobs.opened_at` + `talent_jobs` 入职时间 |
| Offer 接受率 | ✅ `offer` 阶段 → `hired` / `withdrawn` |
| 试用期留存率 | ✅ `probation_end` + 离职日期 |
| 人均产出（HR 每人每月入职数） | ✅ `owner_id` + `hired` |
| 岗位填充率（HC 完成度） | ✅ `headcount` + `hired` 数 |

**数据全在，一个都不用新增字段，只是没算。** 这是投入产出比最高的一项——1 天出 5 个指标，直接变成销售 demo 的第一屏。

### N4【P1】离职闭环清单（仅在走路线 B 时做）

已有 `resignation_date` 和「离职倒计时」提醒，但没有**流程**。真实场景要做的 6 件事：工作交接、资产归还、权限回收、离职面谈、社保减员、开具离职证明。

- `onboarding_items` 的模式可以 100% 复用（改名 `checklist_items`，加 `scene` 字段区分入职/离职）
- 成本：1 天（复用现有表结构）
- 顺带解决一个现有问题：`doc_templates` 里已有「离职证明」模板，但没有流程触发它

### N5【P1】数据自助导出 / 备份

现在只有「当前筛选结果导出 Excel」。客户要迁走、要做年度归档、要应付审计时，**无法自助导出全量**。

- 这既是合规要求（数据可携带权），也是降低采购阻力的卖点（「随时能走」反而更容易被选）
- 建议：admin 一键导出全量 JSON/Excel（分 sheet），或按模块导出
- 成本：1 天

### N6【P2】候选人自助投递 / 进度查询

现在候选人 100% 靠 HR 手工录入或上传简历。缺候选人侧入口。

- 轻量方案：每个岗位生成一个公开投递链接（`/apply/:jobToken`），填表 + 传简历 → 自动进 `talent_jobs` 的 `screening`
- 进阶：投递后给候选人一个查询链接，看自己在第几轮（减少「催进度」的电话）
- 成本：3 天（含公开页、防刷、去重）
- 注意：公开页要过安全评审（这是唯一对外的写入口）

### N7【P2】简历附件全文检索

现在只检索结构化字段（姓名/公司/职位/技能/备注），**简历原文没进索引**。HR 的真实需求常常是「找那个做过 Kubernetes 的人」，而这个信息只存在于 PDF 正文里。

- 依赖 O2 的 FTS5，把解析出的简历文本一起入库
- 成本：在 O2 基础上 +1 天

### N8【P3】开放 API / Webhook

`approval_instances.ext_provider` / `ext_msg_id` 两个字段是**预留但未实现**的外部审批回调。如果要做企业微信/飞书审批对接，这是入口。

- 只在有明确客户需求时做，否则又是死字段

## 3. 建议删除 / 收敛的功能

删除的前提是**有证据表明它没有价值**，不是「我觉得不好」。

### D1 删除 `communications` 表与 README 相关段落

证据：`talents.ts:902` 代码注释自证——

> 「沟通记录功能已下线：全库无写入入口，详情页时间线恒为空，详见 git 历史」

但 `schema.sql:158` 还在建这张表，README 第 13 行还在宣传「沟通记录（电话/微信/面试/邮件，评分 + 跟进提醒）」。

- 动作：删表（或明确保留为历史数据归档）+ 删 README 段落 + 清理 `TalentDetail` 里恒为空的时间线组件
- 注意：如果这张表里有历史数据，先导出备份再删

### D2 删除 `interviews/ai-summary`

证据：`docs/ai-endpoint-audit-2026-10-14.md` 自己判为 **P0 真重叠**——输出结构与 `candidate-summary` 逐字段一致，输入是子集，同页双入口，且线上 0 使用。

- 动作：删端点 + 删前端按钮，统一走 `candidate-summary`
- 收益：少一个用户概念，少 60 行代码

### D3 删除 `resume-optimize`

证据：线上 0 使用。更重要的是**价值存疑**——它是「帮候选人优化简历」，但用户是 HR，HR 不改候选人的简历。这个功能解决的是求职者的问题，不是招聘者的问题。

- 动作：下线，或改造为「给候选人的简历改进建议」（发给候选人，而非 HR 自己用）

### D4 删除或实现 `feishu_open_id` / `wecom_userid` / `notify_channel`

证据：schema 有列，`src/worker` 零引用，前端零 UI。

- 动作：要么按 O3 实现企业微信 webhook，要么删列
- 顺带修 `Landing.tsx:142` 的宣传文案——现在写的「与企业微信打通」是不实描述

### D5 收敛 Match 与 Profiles 两个页面

`/match`（智能匹配）和 `/profiles`（人才画像）共用 `profiles` 权限，是两个页面。git 历史 `e4165c8` 的标题是「**救活** /match 孤岛」——说明它曾经是个没人进的孤立页面。

- 建议：合并为「画像匹配」一个页面（左画像列表、右匹配结果），或把 Match 收进 Profiles 的详情页
- 判断依据：看 `match_profiles` 表有多少条记录。如果 < 10，直接合并

### D6 删除移动端 `/m/funnel`

理由见 O1：手机上的漏斗概览没有行动价值，却占了一个 Tab 位（移动端一共才 4 个）。腾出来给面试。

### D7 删除仓库里的非源码目录

`dist/`（6.9M）、`_promo/`（30M）、`_shots/`（6.4M）、`backups/`（1.5M）——共约 45M 不该进仓库。

- 动作：`.gitignore` + `git rm -r --cached`
- 注意：这是**仓库清理**，不是删本地文件，`_promo` 里的推广素材请先确认是否需要保留

## 5. 三条取舍原则

**① 「数据已经在库里，只是没算」的功能优先做。**
N3（人效指标）和 O5（漏斗分析）是这一类——不需要新增字段、不需要改数据流，只是加聚合查询和图表。它们的投入产出比比「新增一个模块」高一个数量级，因为数据采集的成本早就付过了。

**② 删除比新增更需要证据，但收益同样真实。**
上面每一项删除都有代码注释、审计文档或线上数据支撑，不是主观判断。每删一个零使用的端点，用户的心智负担就少一分——14 个 AI 概念对 HR 来说已经是负担了。

**③ 不要在有战略分歧的地方做战术优化。**
第 0 节的「招聘 vs 招聘+在职」没定之前，不要优化合同页、不要给社保加功能。否则一旦决定走路线 A，这些工作全部作废。
